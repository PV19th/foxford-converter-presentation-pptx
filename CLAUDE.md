# Конвертер презентаций Фоксфорда → веб-приложение

Этот файл — постоянная инструкция для Claude Code. Читай его в начале каждой сессии.

## Что строим

Внутренний сайт для методистов Фоксфорда. Автор отправляет коллегам ссылку, они входят по общему паролю. Коллега загружает старую презентацию урока (.pptx), выбирает шаблон, класс и номер урока и получает файл в новом шаблоне, превью всех слайдов и отчёт о том, что проверить вручную. Базовая конвертация работает без ИИ: сайт запускает готовый конвертер из `converter/`. ИИ подключается позже как дополнительный движок (см. «Развитие»).

Пользователи не программисты. Интерфейс на русском, максимально простой: одна страница, понятные ошибки.

Сайт = страница (HTML/CSS/JS без фреймворков) + серверная часть на Python (FastAPI) в Docker. Чисто статический сайт невозможен: конвертеру нужны Python, LibreOffice и шрифт на сервере.

## Развитие: закладывать сразу

- **Несколько шаблонов.** Всё, что относится к шаблону, — в профиле `templates/<имя>/profile.json` (название для сайта, классы, база, доноры, служебные фразы). Пользователь выбирает шаблон на сайте. Сейчас один профиль «Сегмент 5–11» (ex58 для 5 класса, ex64 для 6-го). Профиль подходит только для шаблонов той же геометрии (4:3); другой формат требует доработки кода или ИИ-движка.
- **Движки конвертации.** Сейчас один — конвертер по правилам. Позже — ИИ-движок. Общие шаги (shrink, verify, превью, памятка) не зависят от движка.
- **ИИ.** Модуль `app/ai/` с общим интерфейсом и провайдерами; первый — Anthropic (Claude), позже, возможно, другие с выбором на сайте. Ключи только из переменных окружения (`ANTHROPIC_API_KEY` и т. п.). Учитывать расход токенов и дневной лимит. Anthropic API недоступен из России — это влияет на выбор сервера.

## Дизайн сайта

Максимально минималистичный, ориентир — balenciaga.com (референсы в `../рефы/`): белый фон, чёрный текст, заглавные буквы в навигации и заголовках, тонкие линии-разделители и сетка, без теней и скруглений, мелкие подписи моноширинным шрифтом. Единственный акцентный цвет — `#FF9900` (кнопки, активные элементы, прогресс); текст на оранжевом — тёмный, не белый (контраст).

## Конвертер — не переписывать

`converter/` — отлаженный код, который вырос из десятков ручных переносов и правок методистов. Логику переноса не меняй и не «улучшай». Если для приложения что-то нужно поменять (например, пути), меняй минимально и сначала спроси.

Как он запускается (подробно в `docs/README_конвертера_как_запускать.md`):

```
cd converter
python3 convert.py старый.pptx новый.pptx 5.3       # номер урока: «класс.урок»
python3 shrink.py новый.pptx новый_сжатый.pptx 18.5 # обязательно, сборка часто > 18 МБ
python3 verify.py старый.pptx новый_сжатый.pptx     # сверка слов: MISSING / EXTRA
```

Переменные окружения (см. `converter/engine.py`, строки ~16–19):
- `CONV_DIR` — рабочая папка; конвертер ищет в ней `assets/` со стикерами. Папки `assets/` в репозитории нет намеренно (см. «Стикеры» ниже). Задавай `CONV_DIR` = корень проекта.
- `CONV_BASE` — базовая презентация. Всегда задавай явно:
  - 5 класс → `base/ex58.pptx`;
  - 6 класс → `base/ex64.pptx`.
- `CONV_DONOR` — для 6 класса обязательно:
  ```
  {"title":1,"plan":3,"wait":5,"summary":16,"reflection":29,"bye":30,"links":31,"dividers":[4,17],"content":[7,7,26,7],"why":2,"think":6,"title_strip_callouts":true,"title_pic":true,"wait_step":1.34,"wait_center":4.18}
  ```
  Для 5 класса не задаётся (используются значения по умолчанию в `convert.py`).

Номер урока (`6.15`) задаёт тег «6 класс» и «Урок 15». Проверяй формат ввода: `^(5|6)\.\d{1,2}$`.

## Стикеры — вручную

Раньше конвертер сам ставил два стикера: «ВАЖНО» (`vazhno.png`) и объёмный «?» (`qmark.png`). В базе стикеров Фоксфорда их около сотни, и методисты подбирают их вручную, поэтому папка `assets/` удалена.

Конвертер для этого уже доработан (функция `sticker()` в `convert.py`): если файла стикера нет, стикер не вставляется, место под него остаётся, а в отчёт по слайду пишется строка `СТИКЕР ВРУЧНУЮ: …`. Если когда-нибудь положить файлы обратно в `assets/`, конвертер снова будет ставить их сам.

Эта доработка не проверялась на реальном прогоне (не было исходных презентаций). На этапе 3 обязательно прогони тестовые файлы, где есть «ВАЖНО» и «Подумаем!», и убедись, что конвертация не падает и строки `СТИКЕР ВРУЧНУЮ` появляются в отчёте.

В веб-приложении собери эти строки в отдельный список в памятке: «Добавьте стикеры: слайд 7 — «ВАЖНО» справа от плашки; слайд 12 — «?» слева внизу».

## Жёсткие технические ограничения

- `engine.py` берёт шрифт по пути `/usr/share/fonts/truetype/open-sans/OpenSans-*.ttf`. Он нужен для расчёта переносов строк, поэтому всё запускается только в Docker на Linux с пакетом `fonts-open-sans`. На Mac или Windows без Docker конвертер работать не будет.
- `soffice` (LibreOffice) нельзя запускать параллельно. Задачи обрабатываются строго по одной, через очередь. Пользователь видит своё место в очереди.
- Рендер превью: `soffice --headless --convert-to pdf`, затем `pdftoppm` (пакет `poppler-utils`) → PNG по слайдам + контакт-лист.
- Python-зависимости — в `converter/requirements.txt`. Свои скрипты не называй `inspect.py` и другими именами модулей стандартной библиотеки.
- Загружаемые файлы до ~100 МБ. Временные файлы удалять через N часов (настраивается).

## Что видит пользователь после конвертации

1. Кнопку «Скачать .pptx».
2. Превью всех слайдов (сетка миниатюр, клик — крупно).
3. Сверку текста: если `verify.py` нашёл MISSING-слова, показать их понятным списком («Эти слова есть в старой презентации, но не нашлись в новой»).
4. Список «Добавьте стикеры» — по строкам `СТИКЕР ВРУЧНУЮ` из отчёта конвертера, с номерами слайдов.
5. Памятку «Проверьте вручную»: пункты, которые конвертер не делает сам (см. раздел «Вручную» в README конвертера и `docs/Чек-лист_переноса.md`): схемы на всю ширину, выравнивание текста в карточках влево, чередование цветов соседних схем, выбор титула под настроение урока, а также схемы со стрелками, таблицы и слайды, где кегль ушёл в 14.

При ошибке конвертера — понятное сообщение и кнопка «Сообщить автору» (пока просто показать контакт; адрес задаётся в конфиге). Полный traceback — в лог, не пользователю.

## Стек и развёртывание

- Бэкенд — FastAPI, интерфейс — одна HTML-страница с простым JS (решено). Код должен быть простым, чтобы его мог поддерживать один человек-непрограммист.
- Docker: один `Dockerfile` + `docker-compose.yml`. В образе: python3, зависимости, `libreoffice-impress`, `fonts-open-sans`, `poppler-utils`.
- Доступ закрыт: на первом этапе — общий пароль из переменной окружения; позже, возможно, корпоративный SSO (решает IT).
- Нужна инструкция для IT в `DEPLOY.md`: как собрать, запустить, обновить, где логи.
- Обновление конвертера должно сводиться к: заменить файлы в `converter/` → пересобрать контейнер одной командой.

## Тестирование

В `test_inputs/old/` лежат старые презентации, в `test_inputs/reference/` — их переносы, принятые методистом. Для каждой пары:
- прогнать через приложение;
- `verify.py` не должен показывать расхождений, кроме служебных кнопок старого шаблона и склеенных слов;
- показать мне превью рядом с эталоном, чтобы я сравнил глазами.

Добавь простой скрипт `tests/run_all.sh`, который прогоняет все тестовые файлы.

## Порядок работы

1. Прочитай этот файл, `docs/README_конвертера_как_запускать.md` и код `converter/`.
2. Предложи план и структуру проекта. Ничего не пиши, пока я не одобрю.
3. Сначала добейся, чтобы конвертер работал в Docker из командной строки на тестовых файлах (база — `ex58`/`ex64`, как сейчас). Сохрани эти результаты: это эталон для этапа 6.
4. Потом — веб-интерфейс и очередь.
5. Потом — `DEPLOY.md`. После этого коллеги уже могут пользоваться приложением.
6. Потом — перевод конвертера на фирменный шаблон как базу (раздел ниже).
7. Потом — ИИ-доработка презентаций (после первых тестов сайта коллегами). Зачем: презентации разных предметов устроены по-разному, и все нюансы одним алгоритмом не учесть. ИИ дорабатывает результат конвертера там, где правила не справляются; конвертер по правилам остаётся основой.

Этапы 3–4 идут локально на Mac автора; сервер и `DEPLOY.md` (этап 5) — когда будет выбран сервер.

## Этап 6: фирменный шаблон как база

Сейчас слайды-доноры берутся из готовых уроков (`ex58`, `ex64`). Цель — брать их из самого фирменного шаблона `base/template_4x3_v01_26.pptx` (150 слайдов). Зачем: больше вариантов титулов, разделителей, планов и рефлексии; выбор титула можно отдать пользователю; при новой версии шаблона достаточно заменить файл.

Что уже известно (подробно — `docs/template/Карта_шаблона_150_слайдов.md`):
- шаблон того же формата (4:3, 10×7,5 дюйма), с той же палитрой и шрифтом Open Sans, что зашиты в `engine.py`. Геометрию, цвета и шрифт **не менять**;
- черновая карта доноров есть в карте шаблона; её надо проверить по миниатюрам `docs/template/миниатюры_*.jpg` (не рендерить шаблон целиком — это дорого и не нужно);
- слайдов «Поставь на паузу» (`wait`) и «Почему стоит посмотреть» (`why`) в шаблоне нет. Предложи, как их подключить. Мой предпочтительный вариант: собрать одну базу «шаблон + эти слайды из `ex58`/`ex64`» скриптом, а не вручную;
- донорские слайды шаблона содержат тексты-заглушки («Текст», «У короля с королевой…» и др., список в карте) — они не должны попасть в результат. Добавь проверку на них в `verify.py` или отдельным шагом;
- `Builder.finish()` удаляет исходные слайды базы, и python-pptx при сохранении отбрасывает неиспользуемые картинки, поэтому размер базы на размер результата не влияет. Всё равно прогоняй `shrink.py`.

Как делать:
1. Вынеси всё, что относится к шаблону, в «профиль»: папка `templates/<имя>/` с базой, `donors.json` (бывший `CONV_DONOR`), служебными фразами (и, если понадобится, стикерами). Профили `ex58` и `ex64` должны давать ровно тот же результат, что сейчас.
2. Добавь профиль `foxford_5-11_v01_26` на базе шаблона.
3. Функции сборки (`build_title`, `build_plan`, `build_summary` и др.) написаны под устройство фигур на слайдах `ex58`. Для каждого типа проверь, подходит ли донор из шаблона, и поправь сборку минимально. Каждое изменение — с прогоном тестов и сравнением с эталоном этапа 3.
4. Если правило в коде противоречит чек-листу (`docs/Чек-лист_переноса.md`), прав чек-лист; спроси меня.
5. В веб-приложении — выбор профиля и, для фирменного шаблона, выбор титула (миниатюры 5–11).

Если появится новая версия шаблона: сожми её `tools/compress_template.py` (оригинал ~114 МБ, GitHub не принимает файлы больше 100 МБ), положи в `base/` и сверь номера слайдов в `donors.json`.
